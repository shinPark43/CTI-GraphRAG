1. Executive Summary & System Requirements

This project builds a knowledge-graph-guided attribution engine that helps a small open-source LLM (Llama-3-8B-Instruct) map threat-report passages to MITRE ATT&CK techniques (CTIConnect task ATA) and CWE weaknesses (task VCA). On CTIConnect, LLaMA-3-8B reaches only 0.28 F1 on ATA and 0.40 on VCA, against 0.90 and 0.76 for GPT-5; the benchmark authors identify attribution as the one task family bottlenecked by model capability rather than retrieval.

Scope change (approved by Dr. Dogdu, Oct 16, 2026). The proposal's four-task, multi-hop GraphRAG evaluation is narrowed to entity attribution only. Entity-linking tasks (RCM, ESD, ATD) already reach about 0.97 F1 with domain-specific retrieval and are single-hop, so they cannot show what a graph adds. Multi-hop questions are no longer required.

Research question. Can a cybersecurity knowledge graph, used as a reasoning scaffold, close the gap between small open-source models and frontier models on CTI entity attribution?

Domain and persona. A SOC or threat-intelligence analyst reads a vendor report and needs the ATT&CK technique or CWE weakness a passage describes, with the reasoning and the KB entry that support it. The system runs its answering model locally (Ollama on a MacBook), so reports are never sent to a commercial LLM.

2. End-to-End System Architecture

The system has an offline build stage that turns official records into a validated Neo4j graph, and a per-question stage in which the graph produces candidates and the small LLM only chooses among them.

3. Knowledge-Graph Schema & Construction

The graph is built only from CTIConnect's corpus_kb snapshot (commit 554797d) and its 321 report summaries. Structure the snapshot already records (ATT&CK hierarchy and tactics, CAPEC links to CWE and ATT&CK, CVE weakness labels) is parsed deterministically with no LLM, and its edge counts match CTIFoundry's for the same snapshot. Outside data (ATT&CK STIX, CWE XML, NVD) and the benchmark's construction/ files, which generated the questions and their answers, are excluded so results stay comparable with the paper; as a consequence the graph has no CWE parent–child hierarchy.

LLM extraction: the report layer

Prose is the only input that needs an LLM. The report summaries become labelled examples of report wording for each technique, following CTIFoundry's build phase (Steps 0 and 2; its entity-mention and resolution steps serve multi-document synthesis, which is out of scope).

  • Chunking: clause-bounded chunks of 200–900 characters, split after ., !, ? or ;, with no overlap. Each chunk keeps exact character offsets into its report, re-verified on load (650 chunks).

  • Prompt: CTIFoundry's TTP-grounding prompt (App. G.3) verbatim, with the tactic list filled from the snapshot. It carries seven few-shot mappings from outcome phrases to techniques ("encrypts files" → T1486) and rules that exclude defenses, generic outcomes and bare tool names. Model gpt-5.4-mini-2026-03-17 in JSON mode; output {"ttps": [{"behavior", "technique_id", "technique_name"}]}.

  • Error handling: an unparseable response yields no records for its chunk. A record is kept only if its ID exists in the snapshot and its behavior phrase occurs verbatim in its chunk; 3,512 of 3,741 extracted records pass.

  • Confidence: the prompt tells the model to omit behaviors it is unsure of, and both checks are hard gates. A graded score, the cosine between a behavior and its technique's text with a threshold set on the 69 gold triples, is the planned extension.

  • Question side: the quoted passage and any CVE, CWE or ATT&CK IDs are taken from each question by regex, never by the LLM.

Entity resolution: names to IDs

Small models recall titles more reliably than numbers, so a generated ID is never trusted on its own:

  1. Exact match: the ID exists in the graph and its title matches the generated name after normalization.

  2. Title lookup: normalized title equality within the target taxonomy.

  3. Retired IDs: follow REPLACED_BY to the current sub-technique.

  4. Embedding fallback: nearest title by cosine similarity, accepted only above a threshold τ tuned on the dev split (initial τ = 0.80); below τ the answer is marked unresolved.

4. Graph Storage, Enhancement & Reasoning

The graph lives in Neo4j 5, which holds the typed nodes and edges and vector indexes over every text the engine searches. The reasoning layer adds three bridges from report wording to taxonomy entries (CAPEC patterns, CVE examples and report-layer behaviors) and derives domain, retired status and tactics as attributes. It never filters candidates by those attributes, because a filter would assume what the answers look like.

Database initialization (schema.cypher)

// schema.cypher (excerpt): 8 uniqueness constraints, 4 lookup indexes, 5 vector indexes
CREATE CONSTRAINT technique_id IF NOT EXISTS FOR (t:AttackTechnique) REQUIRE t.id IS UNIQUE;
// ... the same for Tactic.name and the CWE, CAPEC, CVE, ThreatReport, ReportChunk, ReportBehavior ids
CREATE INDEX technique_title IF NOT EXISTS FOR (t:AttackTechnique) ON (t.title_norm);
// ... cwe_title, technique_domain, chunk_report
CREATE VECTOR INDEX technique_emb IF NOT EXISTS FOR (t:AttackTechnique) ON (t.embedding)
OPTIONS {indexConfig: {`vector.dimensions`: 3072, `vector.similarity_function`: 'cosine'}};
// ... cwe_emb, capec_emb, cve_emb, behavior_emb with the same settings

// the CAPEC bridge (rule R4) for one passage vector $v, exact similarity
MATCH (c:CAPEC) WITH c, vector.similarity.cosine(c.embedding, $v) AS score
ORDER BY score DESC LIMIT 10
MATCH (c)-[:EXPLOITS_WEAKNESS]->(w:CWE)
RETURN w.id AS cwe, sum(2 * score - 1) AS bridge_score ORDER BY bridge_score DESC;

The report layer is stored as (ThreatReport)-[:HAS_CHUNK]->(ReportChunk)-[:HAS_BEHAVIOR]->(ReportBehavior)-[:GROUNDS]->(AttackTechnique). scripts/load_graph.py applies schema.cypher (17 statements) and loads 10,286 nodes, 9,296 of them with embeddings, from the on-disk embedding cache in about 30 seconds, checking every edge count against the Python derivation. Neo4j 5.26 runs locally in Docker.

SGS can take its candidates from Neo4j (--backend neo4j): each bridge is one Cypher query. Evaluation uses exact vector.similarity.cosine, so the Cypher path returns the same rankings as the in-memory reference up to floating-point near-ties; the HNSW vector indexes serve the chatbot, where approximate search is acceptable.

Gold-triple verification (scripts/verify_triples.py)

The engine's answers are scored as triples against data/gold_triples.json: 69 triples (28 DESCRIBES_TECHNIQUE, 41 DESCRIBES_WEAKNESS), one per dev-split question, from CTIConnect's expert-verified answers.

The script reads a run's predictions.jsonl and extracts IDs with CTIConnect's official extract_ids / normalize_id, so triple scores agree with benchmark scores. A predicted triple counts when (report, predicate, ID) equals a gold triple exactly; precision, recall and F1 are reported overall and per predicate. Near misses (the gold technique's parent or child), retired IDs and IDs absent from the snapshot are counted separately, never as hits.

5. Featurization, Embedding & Hybrid Indexing

Candidate generation is the first bottleneck: the small model cannot choose an answer it never sees. This section specifies the text features, the snapshot bridges, two graph embeddings and the indexes, and how their rankings are fused. Every setting is chosen on the dev split by candidate recall@5, which needs no LLM calls; the test split is never used for tuning.

Node featurization

Each searchable node gets one text view from its own snapshot fields, embedded with text-embedding-3-large (E, 3,072 dimensions) and L2-normalized: title + contents for techniques and CWEs, name + Description for CAPEC patterns, the description for CVEs and the phrase itself for report behaviors.

Scoring functions

With e(x) = E(x) / ‖E(x)‖, a dense ranking orders nodes v by s(q, v) = e(q) · e(v). The three bridges score a target t by the similarity of the records that point to it:

S_{\mathrm{B}}(t) = \sum_{x \,\in\, \mathrm{top}_{n_B}(\mathrm{B},\, q),\ x \to t} s(q, x), \qquad B \in \{\mathrm{CAPEC}\ (n=10),\ \mathrm{CVE}\ (n=20),\ \mathrm{Report}\ (n=30)\}

Report behaviors from the question's own source report are excluded. Rankings are fused by reciprocal-rank fusion:

\mathrm{RRF}(v) = \sum_{r \in R} \frac{1}{60 + \mathrm{rank}_r(v)}

Queries and chosen configurations

Two queries are built per question: the full question q_Q and its quoted passage q_P. The passage alone retrieves worse than the full question, so the full question stays in every configuration.

  • ATA: RRF of [RRF(dense(q_Q), dense(q_P)) and S_Report(q_P)] over all 1,076 techniques.

  • VCA: RRF of dense(q_Q) over CWE records, S_CAPEC(q_P) and S_CVE(q_P).

Considered and dropped. BM25 keyword search and, for ATA, the CAPEC bridge (only 177 CAPECs map to ATT&CK) lowered fused recall in pilot measurements. Domain and retired-ID filters are left out because they encode an assumption about the answers. Re-ranking VCA candidates by their single closest CVE example lost to the CVE vote.

Graph representation learning

Two graph embeddings are specified over the snapshot graph G = (V, E) of Section 3: 9,315 nodes (techniques, tactics, CWEs, CAPECs, CVEs, report behaviors) and 10,276 undirected edges. The edge set is a design choice: taxonomy (SUBTECHNIQUE_OF, REPLACED_BY, IN_TACTIC), links (EXPLOITS_WEAKNESS, MAPS_TO_TECHNIQUE, HAS_WEAKNESS) and report (GROUNDS).

A. Propagated text embeddings (training-free GraphSAGE-mean, APPNP form). Each node starts from its text embedding x_v = e(text(v)) and mixes in its neighbors' vectors:

H^{(0)} = X, \qquad H^{(k+1)} = (1-\alpha)\,X + \alpha\,D^{-1}A\,H^{(k)} \quad (k = 0, \dots, K-1), \qquad h_v = \frac{H^{(K)}_v}{\lVert H^{(K)}_v \rVert}

A is the adjacency over the chosen edge set and D its degree matrix; isolated nodes keep x_v. The vectors stay in the text space, so a question is scored directly: s_A(q, v) = e(q) · h_v. One hop folds a CWE's CVE examples and CAPEC patterns into it, and a technique's parent, sub-techniques, tactics and report examples.

B. Text + node2vec. A structural embedding g_v of 128 dimensions is learned by node2vec: second-order random walks with return parameter p and in-out parameter q, then skip-gram with negative sampling over each node's walk context N_W(v):

\max_{g} \sum_{v \in V} \sum_{u \in N_W(v)} \Big[ \log \sigma(g_u^{\top} g_v) + \sum_{j=1}^{5} \mathbb{E}_{w \sim P_n} \log \sigma(-g_w^{\top} g_v) \Big]

A question is not a node, so it is anchored through its 10 nearest KB nodes by text, and the two similarities are added:

g_q = \mathrm{normalize}\Big(\sum_{i \in \mathrm{NN}_{10}(q)} \max(s(q,i), 0)\, g_i\Big), \qquad s_B(q, v) = s(q, v) + \lambda\, g_q^{\top} g_v

Leakage guard. Report-behavior edges from the question's own report are removed before propagation; during evaluation the vectors are recomputed per held-out report, while the deployed chatbot uses the full graph. node2vec is trained on the corpus_kb edges only, without report behaviors.

Use in the methods. A graph-embedding ranking scores targets for the question and for the passage, fused by RRF like the other rankings. It enters two evaluation rows (Section 7): GE-RAG, vanilla RAG's prompt over the GE top 5, and SGS + GE, the GE ranking added to SGS's fusion.

6. Attribution QA Engine & Prompt Templates

The method, Snapshot-Guided Selection (SGS), gathers 5 candidates and their evidence from the snapshot graph and lets the small model make one constrained choice among them. Its configuration was frozen on the dev split and is implemented in src/ctiattr/sgs.py; the baselines reuse CTIConnect's prompts verbatim, so the method is the only difference.

Baselines

MethodStepsSource
CB: closed-bookquestion → answerCTIConnect closed_book, prompts verbatim
VR: vanilla RAGembed full question → top-5 raw KB records (600 characters each) → answerCTIConnect vanilla_rag, prompts verbatim
DtR (reference row)decompose → retrieve per behavior → aggregateCTIConnect released code; not reproducible as described in the paper (Section 7)

The VR answer prompt is CTIConnect's, unchanged: the question, the retrieved records, then "Based on the candidates above, answer the question. Cite the single best-matching identifier explicitly."

SGS procedure (frozen)

  1. Parse. Extract the quoted passage and any CVE, CWE or ATT&CK IDs by regex.

  2. Candidates. Run the chosen configuration of Section 5 and keep the top 5.

  3. Evidence cards. One line per candidate, built only from the snapshot:

    • ATA: ID | title | tactics | platforms | detection: <first sentence> | report examples: "<snippet>"; "<snippet>", the two report-layer sentences closest to the passage, never from its own report.

    • VCA: ID | title | consequences | related attack pattern: <CAPEC name> | example vulnerability: <closest CVE description>.

  4. Choice. The model returns one ID; JSON-schema structured output restricts it to an enum of the 5 candidate IDs, so an invented ID is impossible.

    • ATA: one call, candidates in retrieval order.

    • VCA: five calls over the cyclic rotations of the 5 candidates (each appears once in every position), majority vote, ties to the better retrieval rank. This cancels the position bias seen in pilot runs, where the 8B model favored early list positions.

  5. Answer. Exactly one ID plus its title. A final check confirms the ID is one of the listed snapshot IDs and the title contains no other identifier, since the official scorer counts every ID in the text.

Prompt (exact)

System: You are a cyber threat intelligence analyst. Output schema: {"id": enum of the candidate IDs}.

You are mapping a threat-report passage to {MITRE ATT&CK techniques | CWE weaknesses}.

Passage:
"{passage}"

Candidates:
{cards}

Choose the ONE candidate that best describes the behavior in the passage. Judge by
what each candidate means, not by shared words. Return JSON with its id.

Answer generator prompt (exact). After the choice, a second call writes the answer the chatbot shows and RAGAS scores. Any other ATT&CK, CWE or CAPEC identifier in its output is replaced by that entry's title, so official F1 is unchanged.

The passage below was attributed to {id} — {title}.
Evidence: {card}
Passage: "{passage}"
Answer the user's question in 3-5 sentences: {question}
Mention no other ATT&CK, CWE or CAPEC identifier.

Alternatives considered. Ten candidates instead of five lowered selection accuracy even when the gold was listed. A pairwise tournament needed up to 8 calls with no gain over one listwise call, and a rotation vote for ATA gained nothing once report examples were on the cards. Tactic-first narrowing is covered under R3, and an output fact-checker is unnecessary because the enum restriction and the final check already block invented IDs.

7. Evaluation Pipeline & Benchmark Protocol

All methods are scored with CTIConnect's official identifier F1 on its 379 attribution questions (ATA 160, VCA 219), with the same model, embedder and data, so differences come from the method alone. Configurations are chosen on the 73-question dev split; the 306-question test split stays untouched until the final evaluation, where each method runs on it once.

Data and splits

  • Questions: CTIConnect data/entity_attribution, pinned to commit 554797d. Every question has exactly one gold ID.

  • Split by report: questions are split by source report (seed 13), so no report's passages appear on both sides: dev 73 questions from 29 reports (30 ATA, 43 VCA), test 306.

  • Quick-look set (eval_queries.json): 20 dev questions (10 ATA, 10 VCA), for fast checks and the human evaluation. They are single-hop (passage → one ID) by design, under the approved scope change (Section 1).

  • Known ceiling: two pairs of ATA questions are word-for-word identical but have different gold IDs (e.g. ata-106 T1105, ata-107 T1059), so maximum ATA F1 is 0.988.

Scoring rule: a failed call is scored as an empty answer (F1 = 0), never dropped. CTIConnect's own aggregator drops missing predictions, which would inflate scores.

Models and comparison

  • Answering model: Llama-3-8B-Instruct only, the smallest model in CTIConnect's Table III, served by Ollama at full precision (fp16), temperature 0. Restricting the study to one model keeps every comparison on the same footing within the project's time.

  • Compared methods: CB and VR (CTIConnect's baselines), SGS (Section 6), and the two graph-embedding rows of Section 5: GE-RAG and SGS + GE. Each pair differs in one component, so the comparison isolates it.

  • DtR as a reference row only. The paper describes DtR as decompose → canonicalize → retrieve, but the released code has no canonicalization step and the paper publishes no prompts, so its 0.28 / 0.40 cannot be reproduced.

  • Reported per method: identifier P / R / F1 and exact match per task and overall, candidate recall@k, IDs per answer, triple P / R / F1, RAGAS means on the 20 eval queries and the human ratings below.

  • Significance: paired bootstrap 95% confidence intervals (10,000 resamples) on F1 and McNemar's exact test on exact match, for SGS vs VR and for each graph-embedding row vs the method it extends.

RAGAS configuration

Setup: scripts/ragas_eval.py, RAGAS 0.4.3 collections metrics, judge gpt-5.4-mini-2026-03-17, embeddings text-embedding-3-large. Contexts are exactly what each method showed the model (SGS: the 5 evidence cards; VR: the 5 KB records at 600 characters). References are CTIConnect's reference answers, which also cover the questions' extra asks (likelihood of exploit, affected platforms, consequences).

Risks and mitigations

RiskMitigation
Retrieval caps every method: the gold ID must reach the 5 candidates the model seessnapshot bridges and graph embeddings fused by RRF (Section 5); recall@k reported beside every F1
Small samples: on 20 questions one answer moves F1 by 0.05–0.10decisions made on the 73-question dev split; final claims only from the 306-question test split, with bootstrap CIs
Settings and prompts overfit the dev questionssmall search grids reported in full; dev numbers labelled as such; the test split is run once at the end
